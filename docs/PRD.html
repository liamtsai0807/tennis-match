TennisPal 網球夥伴

幫網球愛好者找到程度相近的球伴，約一個對兩個人都方便的球場打球。

版本 v0.3 日期 2026-08-22 狀態 MVP 已可操作，未上線 對應程式碼 commit 64ec596

§0這份文件怎麼讀

這不是先寫規格再開發的 PRD。順序是反過來的：先做出可操作的原型， 再把當中的決策與取捨寫下來。所以文件裡的每一條規格都對得上實際跑得起來的程式碼， 也標了哪些是還沒做、哪些是需要你決定。

三種標記貫穿全文：

已實作 程式碼裡有，而且在瀏覽器實際點過。
未實作 有明確規格，但還沒寫。
待決 需要產品決策才能往下，寫在 §9。

§1要解決的問題

想打網球的人，卡在兩件事上：找不到人，或找到的人程度差太多。

第二件比第一件嚴重。網球是一對一的隔網運動，兩個人的程度差距會直接毀掉整場球—— 強的那方在餵球、弱的那方在撿球，雙方都不會想再約第二次。這跟籃球、羽球團體或多人的場合不同， 那些場合程度不齊還能靠人數稀釋掉。

台灣現況是：訂場走球館各自的網站或電話，找人走 LINE 群組和社群貼文，兩件事完全分開。 既有工具解決的是「訂場」，沒有人解決「媒合」。而媒合失敗的成本， 使用者是在球場上才付的。

產品的核心賭注

把「找人」和「訂場」合成同一個動作，並且讓程度媒合準到使用者願意相信它。 如果媒合不準，這個產品就只是一個比較難用的訂場網站。

§2目標使用者

主要

都會區的休閒球友，NTRP 2.5–4.0，每週打 0.5–2 次，心裡有兩三個固定會去的球場。 有一起打球的人，但不夠穩定——約不到人的那週就不打了。

次要

剛上完初學課程、想找人對打練習的人。他們最痛，因為完全沒有球友圈， 但也最難服務——程度太低，願意陪打的人少。

明確不服務

  • 競賽選手。他們有教練和固定訓練夥伴，不需要媒合。
  • 純社團揪團。「四個人打雙打」是另一種產品（多人揪團看板）， 機制和一對一媒合不一樣，硬做在一起兩邊都做不好。

§3核心使用者故事

User Story

使用者想找與他程度相當或相近的網球同伴約網球場打球。 登錄時可以先設定自己偏好的球場、偏好的時段、偏好的球伴等級。

整個 MVP 就是這一句話，沒有別的。完整流程五步：

01登錄設偏好程度、時段、球場
02找球伴選一天 + 一個時段
03選球場對兩人都方便
04送出邀約同時把場地訂下來
05成局對方接受

§4範圍

§5功能規格

5.1登錄與偏好設定已實作

第一次開啟一律導到登錄流程，填完才放行到主畫面。四個步驟，每一步沒填完不能往下—— 最後一步才發現前面填錯很煩。

步驟欄位可往下的條件
1名字、程度三題名字非空 且 三題都答完
2活動範圍（行政區）、想找的球伴程度區間下限 ≤ 上限
3有空的星期、有空的時段兩者各至少選一個
4常去球場（可複選）至少選一個
  • 偏好一律留白。不預先勾選任何球場或時段——預先勾好等於幫使用者決定， 他會直接按下一步，然後拿著一組不是自己的偏好去媒合。
  • 活動範圍只到行政區。存的是該區中心座標，不問完整地址。 問地址會嚇跑一半的人，而媒合只需要粗略位置就夠準。
  • 之後可改。「我的 → 我的偏好」用的是同一份欄位元件， 不會出現設定頁改了、登錄流程沒改的情況。

5.2程度評估：三題推算已實作

不問「你的 NTRP 是多少」。沒打過分級賽的人不知道 3.0 和 3.5 差在哪， 自評的結果有人虛報有人謙虛——而整個媒合都建立在這個數字上，這是最脆弱的一環。

題目選項在演算法中
跟程度差不多的人對打，通常能來回幾球？ 三球內失誤 / 五到十球 / 十球以上還能控落點 / 能主動變速變旋轉進攻 定基準
2.0 / 3.0 / 4.0 / 5.0
打多久了？ 半年內 / 半年–2年 / 2–5年 / 5年以上 +0 / +1 / +2 / +3
多常打？ 一個月幾次 / 每週一次 / 每週兩次以上 ×2 權重
+0 / +2 / +4

練習量 = 頻率×2 + 年資，範圍 0–7。≤2 扣半級，≥5 加半級，中間不動。 結果夾在 NTRP 2.0–4.5。

兩個權重上的取捨

回合數的四個等級刻意隔開一整級，而練習量只做半級微調。 隔半級的話，球齡就能整個抵銷回合數，等於讓推測值蓋過實際觀察到的行為。 第一版兩者都設 ±0.5，測試立刻抓到「打五年但三球失誤」和「打半年但能來回十球」同分。

頻率權重是年資的兩倍。每週兩次打半年，打得贏每月一次打五年的。

  • 上限壓在 4.5。再上去的差別（發球威脅、戰術層次）自評問不出來， 硬推上去只會讓強手被配到打不動的對手。
  • 逃生路徑。打過聯賽、真的知道自己分級的人，可點「我知道自己的 NTRP」直接選。 資料上記為 level_answers: 'manual'。
  • 顯示白話優先。畫面上主要顯示「能控制球路」，NTRP 數字降級成括號附註。

5.3球伴媒合已實作

選一天 + 一個時段，系統列出候選人。預設值直接吃登錄時填的偏好，多數情況打開就有結果。

合適度計算

訊號權重為什麼
程度接近0.30程度差太多兩邊都打得不開心，見 §1
共同偏好球場0.25決定「約不約得成」
那天那個時段有空0.25同上
雙向合適0.10我也在對方想找的程度範圍內，成功率高很多
距離0.10已經有共同球場的話，住哪沒那麼要緊
  • 硬過濾：對方程度不在「我設定的區間」內就不出現。結果少於三筆時， 畫面提供「放寬程度範圍」一鍵切換。
  • 那天沒空的一律排在有空的後面，即使分數更高——再合適，約不到也沒用。
  • 每一筆都附理由。「程度跟你一樣」「有 2 個共同常去的球場」「晚上通常有空」 「對方也在找你這個程度」。媒合結果不解釋的話，使用者不會信它。
  • 距離用直線距離（Haversine），不是路程。要接路網 API 才算得出路程， 而拿來排序的結果幾乎一樣。

5.4球場推薦已實作

球場不是依「離你多近」排序，而是對兩個人都方便。 只顧自己的話永遠約在自家門口，對方跑到厭世就不會想再約第二次。

因子權重算法
雙方偏好0.40兩人都常來 = 1.0；只有一人 = 0.25；都不是 = 0
較遠那方的距離0.401/(1+worst/15km)，worst = max(兩人距離)
公平性0.201/(1+gap/10km)，gap = 兩人距離差
兩個非顯而易見的決定

用雙曲線衰減，不用「超過 N 公里就歸零」。 歸零會讓所有遠距離同分——對方在新竹時，30 公里和 60 公里的球場得分一樣， 排序就只剩偏好在作用，會推薦出很荒謬的結果。這是測試抓到的。

單方偏好只給四分之一權重。「我常去」是順便， 不該壓過「對方要多跑二十公里」這種硬成本。

  • 每張球場卡同時顯示兩個人各自要跑多遠，並標「兩人都常來 / 你常來 / 對方常來」。
  • 對調兩人身分，推薦順序不變。有測試釘住這個對稱性。

5.5邀約與訂場已實作

關鍵決定

送出邀約的同時就把場地訂下來。 反過來（等對方答應才訂場）常常撲空，好時段撐不到對方回覆。 代價是要處理退訂，這由狀態機保證。

邀約狀態轉換

從動作到對場地的影響
—發起人送出pending建立預約（自動配一面沒被佔用的場）
pending收件人接受accepted不變，預約保留
pending收件人婉拒declined自動退訂
pending發起人取消cancelled自動退訂
  • 不會留下孤兒場地。任何非成局的結束路徑都會退訂，球場不會被沒人要打的球局佔著。
  • 防重複訂場的最後一道防線在資料庫。 bookings 上有 (court_id, date, hour) where status='confirmed' 的唯一索引。前端檢查一定有 race condition，資料庫這層沒有。
  • 邀約若建立失敗，剛才訂的場要退掉，不能留下沒有邀約指向的預約。

5.6PWA、離線與版本更新已實作

  • 可安裝。manifest 帶 192/512/maskable PNG 圖示。 Android 接 beforeinstallprompt 給安裝鈕；iOS 沒有這個事件， 改成教使用者按「分享 → 加入主畫面」。
  • 離線可用。Service worker：帶雜湊檔名的資源快取優先，其餘先連網。 查快取必須 ignoreVary: true——靜態主機會回 Vary 標頭， 而 caches.match() 預設要比對它，離線時請求標頭對不上就整個失效。
  • 版本可見。每次建置產生「日期-git短雜湊」，顯示在「我的」頁最下面。 測試者回報問題時，第一個要問的就是「你哪一版」。
  • 更新提示。App 回到前景時比對 version.json，不一樣才提示。 不用 service worker 的 waiting 狀態判斷——導覽走 network-first， 有網路時冷啟動拿到的本來就是最新的，那時再提示是騙人的。

5.7帳號與登入未實作

目前寫死一個使用者（ME = 'p-me'），「登錄」只是填偏好，不是註冊。 這是上線前的最大缺口：沒有帳號就沒有雙向互動， 你送出去的邀約永遠不會有人回。

  • 需要：註冊、登入、身分驗證、以及把 schema.sql 註解裡那組綁 auth.uid() 的 RLS 政策換上去。現在的政策是「誰都能讀寫」，只適合自己玩。
  • 登入方式待決，見 §9。

§6資料模型

欄位名稱刻意與 src/lib/types.ts 一字不差，程式碼可以直接寫入整個物件，不用做欄位對應。

表關鍵欄位備註
clubs id, name, district, lat, lng, surface, indoor, lights, price_per_hour, courts, open_hour, close_hour 座標是媒合的必要條件，沒有就算不出距離
courts id, club_id, name 一個球館多面場，訂場配到的是「面」
players id, name, ntrp, lat, lng, level_answers, availability, pref_club_ids, pref_ntrp_min, pref_ntrp_max 球友資料就是偏好設定，不另開 preferences 表——媒合要同時看雙方偏好， 拆表只會讓每次媒合多一次 join
bookings id, club_id, court_id, user_id, date, hour, status 唯一索引擋重複訂場
invites id, from_id, to_id, club_id, booking_id, date, hour, message, status 指向它訂的那筆預約，退訂時才找得到

兩個刻意的模型決定

  • availability 用「星期 × 時段」而不是行事曆。 要球友填「週三 19:00–21:00」這種精確格式，沒有人會維護。不精確，但填得完。
  • level_answers 是一個和型別：null（未設定）/ 'manual'（自己選的）/ 三題作答物件。一個欄位表達三種狀態， 比多開一個 level_source 再去對齊兩者乾淨。

§8對照 TIEPLAYER

參考對象是葡萄牙的 TIEPLAYER。以下只根據其首頁截圖上看得到的功能入口整理， 沒有實際使用過，所以不評論它各項功能做得如何。

TIEPLAYER 首頁可見的功能TennisPal判斷
Book a Court（訂場）有核心，兩邊都有
Matchmaker（媒合）有我們把它當主軸，且會解釋推薦理由
Favourite Club（最愛球館）有我們的「常去球場」是複選，且直接餵進媒合演算法
Open Matches（開放球局）無刻意排除，見 §4
Tournaments（賽事）無需要協會合作，不是軟體問題
Classes（課程）無供給端是教練，另一套生態
Match Recordings + AI Insights（錄影與分析）無需要球場硬體，資本密集
Wallet（錢包）無牽涉金流，見 §4
從這個對照學到的

TIEPLAYER 是一個成熟產品的樣子：它同時是訂場平台、賽事平台、教學平台和硬體服務。 那些功能各自都需要供給端的合作關係——球館、協會、教練、攝影設備。

我們沒有那些關係，所以不能從那裡開始。 唯一純軟體、不需要任何合作就能做好的，是媒合。把媒合做到使用者願意相信， 才有籌碼去談後面那些。這也是為什麼我們刻意把即時賽況砍掉——它看起來很酷， 但它不是那個籌碼。

§9待決事項

這些需要產品決策，不是技術問題。標 待決 的規格都卡在這裡。

#問題影響
Q1 登入方式？手機簡訊 / Email / LINE Login / Google 台灣市場 LINE Login 轉換率最高，但綁定 LINE 生態；簡訊有成本； Email 最便宜但流失最多。決定後才能寫 §5.7
Q2 真實球館資料從哪來？人工建檔 / 公開資料 / 球館合作 目前九個球館全是編的。這是上線的硬門檻——資料不真，媒合再準也沒用
Q3 訂場是真的訂到嗎？ 目前是 App 內部的模擬。要真的訂到，得跟球館的系統對接或走人工確認。 這決定產品是「工具」還是「平台」
Q4 先做哪個區域？ 媒合產品有密度門檻——同一區沒有足夠的人，演算法再好也配不出來。 建議先鎖單一區域做深
Q5 要不要做賽後互評？ 打完問一句「跟他打起來？程度差不多 / 對方強一點 / 對方弱一點」， 用真實對戰慢慢校正雙方的 NTRP。這是讓程度數字從「自評」變成「實測」的唯一路， 也是 UTR 那類系統準的原因。但要等有真實使用者互動才有意義
Q6 商業模式？ 免費 / 場地費抽成 / 球館付費曝光 / 訂閱。現在不急，但它會回頭影響 要不要做 Wallet 和訂場對接

§10成功指標

不看註冊數和 DAU——這種產品可以靠好奇心衝高一次註冊，然後完全不用。 要看的是媒合這件事本身有沒有成立：

指標問的是及格線
邀約發送率看到推薦名單後，有多少比例真的按下邀約推薦不夠準的話這裡就掛了
邀約接受率雙向合適的權重有沒有用> 50%
回頭再約同一人的比例這是最重要的一個—
爽約率訂了場但沒去。太高就要考慮押金或信用機制—
放寬條件的使用率太高代表推薦池太小，是密度問題不是演算法問題—
為什麼「回頭再約同一人」最重要

媒合成功的定義不是「約成一場」，是「找到一個固定球伴」。 使用者真正的痛是「每週都要重新找人」；只要有人再約同一個人第二次、第三次， 就代表演算法真的配對了合得來的人——那才是這個產品的價值被證實的時刻。

§11上線前必補

依阻擋程度排序，前兩項不做就不能給陌生人用。

  1. 帳號與登入（§5.7）——沒有它，雙向互動不存在
  2. RLS 政策收緊——現在是「誰都能讀寫」
  3. 真實球館資料（Q2）——資料不真，媒合再準也沒用
